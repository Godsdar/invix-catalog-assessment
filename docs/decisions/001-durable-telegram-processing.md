# ADR-001: Telegram inbox/outbox и диалоги в PostgreSQL

Статус: принято. Дата: 2026-10-20.

## Контекст

Несколько реплик бота не могут безопасно выполнять независимый long polling одного токена. In-memory FSM теряется при перезапуске и расходится между репликами. Telegram повторяет updates, а PostgreSQL, S3 и Telegram Bot API не имеют общей транзакции.

## Решение

Webhook является коротким аутентифицированным входом: записать update по уникальному ID, commit, ответить 200. Рабочие процессы читают PostgreSQL с `FOR UPDATE SKIP LOCKED`, выполняют aiogram handler и фиксируют бизнес-изменения вместе с outbox. Незавершённый ранее принятый update блокирует следующие известные update этого чата. Новые update, которые ещё не дошли до webhook, нельзя упорядочить заранее; абсолютный порядок сетевой доставки не гарантируется.

Одна транзакция обработки удерживает строку задания во время коротких внешних операций. Это осознанный компромисс для небольшого каталога: нет lease/heartbeat и гонок истечения аренды. Времена ожидания Telegram и S3 ограничены, пул ограничен. При большом трафике следует выделить загрузку медиа в отдельную стадию, добавить leases и метрики, не удерживая соединение на загрузке.

Состояние диалога хранится в PostgreSQL и привязано к user ID администратора. Изображение записывается в приватный MinIO по детерминированному ключу до commit товара. Сбой после S3 безопасно повторяет запись. Исходный update остаётся источником повторной обработки; готового товара до commit нет.

Ответы отправляются из outbox отдельными шагами. Telegram не поддерживает идемпотентный ключ `sendMessage`: crash после отправки до записи результата может дать повторный ответ. Не обещаем exactly-once для ответа; уникальный `source_update_id` предотвращает второй товар.

## Альтернативы

- Polling в каждой реплике: конфликты Telegram и невозможность корректного горизонтального масштабирования.
- Redis FSM и отдельная очередь: возможны, но увеличивают число систем хранения и границы согласованности для двух операций каталога.
- Вся обработка внутри HTTP webhook: подтверждение Telegram зависело бы от загрузки S3 и отправки ответов. Durable inbox позволяет принять update до этих шагов.
- Публичный S3 bucket: проще, но открывает список/доступ к объектам без контроля приложения. В этой реализации изображения выдаются API по существующему товару.

## Последствия

Нужны мониторинг очереди, отдельный init и внешний HTTPS. Приложение масштабируется независимо; доступность одиночных PostgreSQL/MinIO и Nginx в Compose ограничивает весь стенд. Повторяющийся сбой блокирует конкретный чат до восстановления/ручного разбора; задания не удаляются автоматически.
